# 周期性回收的触发策略与参数依据

本期引擎只有显式 `collect`，不自动触发。长期运行的服务需要自己安排
周期性触发，建议按「写操作计数 + 时间兜底」双条件：

- 每累计 `N` 次写操作（`new`/`ref`/`unref`/`unpin`）触发一次 `collect`；
- 或距上次 `collect` 超过 `T` 秒即触发一次（取先到者）。

参数依据：

- 单次 `collect` 成本为 O(存活对象数 + 存活边数)，实测 20 万存活对象、
  20 万条边的堆上扫一遍约 0.1～0.2 秒（见 docs/perf.md）。
- 环垃圾的积累速率与请求量成正比：每产生一批互引对象且外部持有解除，
  就新增一批只有 `collect` 能回收的对象。
- 取 `N` 使两次扫描之间积累的垃圾远小于常驻堆（例如 `N` ≈ 存活对象数的
  1/4～1/2），取 `T` 兜底低流量时段（分钟级），即可把环垃圾的驻留时间
  控制在一次扫描周期内，内存曲线呈锯齿而非单调爬升。
- `samples/scripts/06_temp_burst.script` 即按此形态构造：每 50 个临时
  对象一次 `collect`，末尾再回收一个 4 节点环。

注意：`collect` 是「全量标记 + 整体回收」，不是增量/并发回收；触发时
会暂停处理脚本语句，单次停顿与存活规模成正比，安排频率时要把这个
停顿算进延迟预算。
